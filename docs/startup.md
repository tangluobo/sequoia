# 应用启动优化

默认 WGPU 配置会同时创建并枚举多种图形 API。这台 Windows 机器最终选择 NVIDIA Vulkan，但启动时仍加载了 DirectX/OpenGL 及其适配器，增加启动等待和空闲内存。旧版 1295 的分项日志保存在 `target/window-probes/startup-baseline-1307`；这是定位样本，不用作最终性能对比。

`apps/tomato/src/main.rs` 在 Windows 默认设置下启用首选后端策略。`vendor/eframe/src/native/wgpu_initialization.rs` 先尝试 Vulkan，并实际完成适配器、设备和原生表面的初始化；成功后复用这份状态。初始化失败，或首选 API 仅提供 CPU 渲染器时，释放尝试中的资源，再使用原始完整配置。设备参数、内存提示、表面延迟和自定义设备工厂继续沿用。已有图形状态、自定义适配器选择器，以及显式 `WGPU_BACKEND`/`WGPU_POWER_PREF` 设置保留原流程。

没有改变字体、栅格化、图标、DPI、布局、渲染着色器或旧配置。根窗口继续在第一帧绘制后显示，连接树和文本参与首帧，不提前展示空壳。诊断开关开启时，记录图形、输入/剪贴板、无障碍、字体和配置阶段，不记录配置内容或凭据；正常启动无日志和额外定时器。字体及旧配置在诊断样本中合计约 25 ms，保留原流程。

## 验证方法

- 严格 workspace Clippy、全目标构建、格式检查、默认测试和 CLI 自检。
- `apps/tomato/tests/startup.rs` 原生窗口夹具故意让第一次真实设备请求失败，断言原设备工厂被再次调用且最终窗口绘制并正常关闭。它不连接保存主机，也不注入系统输入。
- `scripts/qa/startup.py` 复制冻结的新旧 EXE，分别用空配置和隔离复制的旧连接/全局配置，自动后端与显式 Vulkan 各预热一次，再交错测量三次。只复制连接和全局配置，不安装 DDNS/开发等定时任务，也不打开连接。
- 计时从创建进程前开始，只读枚举该 PID 的窗口，直到发现第一帧绘制后显示的根窗口。截图用于核对字体、图标、连接树及布局，截图夹具自身的 700 ms 等待不计入首屏时间。这是缓存预热后的本机结果，不是重启后的冷启动或显示器扫描输出时间。
- 自动图形模式回归主窗口、RDP 标签/独立窗口及最小化关闭、显式 DirectX 全屏子窗口，以及真实进行中的分片上传退出。旧配置、前版 EXE、锁文件与图标分别校验。
- 同批 release 空闲内存测量分别列工作集和私有提交，不把空闲值当作活动连接峰值。
