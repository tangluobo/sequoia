# 主程序与 RDP 关闭

关闭主程序原先在 eframe 的 GUI 线程调用 `runtime.block_on`，依次等待开发进程、ADB、各文件会话、上传分片和证书 DNS 清理。独立 RDP 的 Windows 剪贴板 HWND 也在 GUI 线程；按需渲染远端格式时，`recv_timeout(10s)` 会阻止主窗口和 RDP 窗口处理关闭事件。已有的 DestroyWindow 防护只能阻止销毁时发起新的读取，无法中断此前正在等待的读取。

主程序现在使用 Running → 清理中 → 完成的退出流程。已有未保存内容确认、服务器配置保存失败保护保留；接受退出后，先统一取消任务，再在 Tokio 后台并发停止文件/SSH 会话、开发进程和各种清理。ConPTY 的同步释放进入阻塞工作池。清理中仍处理原生事件并绘制状态，重复关闭不会重复创建清理任务，完成后请求真正关闭。`on_exit` 仅保留非阻塞的幂等兜底，运行时的最后等待上限为 100ms。

保留远端清理的安全等待：文件/ADB 各有 6 秒边界，RDP 工作线程 2 秒，开发工作队列 4 秒；已启动的证书 DNS 清理保留原 40 秒宽限。这些独立等待并发执行，不在 GUI 线程串行叠加。网络故障下的清理不承诺都能在一秒内完成，也不通过直接杀进程跳过 multipart abort 或 DNS 清理。

RDP 的剪贴板 HWND、OLE 文件对象及消息泵改由每个启用剪贴板的连接自己的 STA 持有，在同一线程创建和销毁。关闭句柄在 UI 线程只发取消信号，先唤醒等待中的文件读取，再中断原生格式读取；格式读取每 20ms 检查取消。协议工作线程负责等待 STA 退出，UI 不 join。消息泵采用 GetMessage，无空闲轮询；未打开 RDP 时不创建这类线程。图形、光标、声音、文件分块与旧连接字段不作更改。

Java 参照为 `RdpConnectHandler` 的独立窗口隐藏后断开会话及标签关闭联动。本次更改保留这些窗口与标签的所有权规则。

隔离 Windows 子进程使用私有窗口站验证了正常按需渲染、已物化文本保留、真实待响应读取的取消、STA 上销毁和无绘制时的所有者回调；不写用户交互桌面的剪贴板。当前证据为 `target/shutdown-clipboard-final-1288.log`，待响应读取取消至 HWND 销毁约 39ms。

开发版原生证据为 `target/window-probes/shutdown-native-dev-1291/validation.json`。覆盖空闲主窗口、有 RDP 标签/独立窗口时关闭整个应用、仅关闭子窗口、双窗口最小化、DirectX 12 全屏关闭，以及实际暂停中的 S3 multipart 上传退出。子窗口移除约 38–160ms，主程序正常退出约 167–461ms，上传退出约 230ms 且完成 AbortMultipartUpload。旧 EXE 正常空闲/连接场景本来即约 168–305ms；本次解决的是等待和取消期间的 GUI 阻塞，不据这些普通场景宣称普遍加速。

这些网络场景仅连接自有 loopback TLS/CredSSP RDP 与 S3 服务，原生窗口命令触发 Close，未注入操作系统输入，未连接用户保存的主机。539 项默认回归通过，76 项按环境条件忽略；格式、严格全目标 Clippy、全目标构建、CLI 自检及冻结的 2200 个生产文件校验通过。五项 RDP 文件剪贴板向量通过，覆盖真实文件分块、跨远端转发、断开唤醒、旧快照失效和重连；见 `target/shutdown-client-unit-1293.log`。
