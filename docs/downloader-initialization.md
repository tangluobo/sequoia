# Downloader initialization repair

The literal `下载器初始化失败` came from a missing optional UI state, before the download actor or HTTP client was started. The tool catalog initialized that state in `TomatoApp::open_tool`, while a saved `TOOL/downloader` connection used `tabs::create_tab` and omitted it. The prior controls test exercised only the catalog entry.

Read-only Java reference: `module/connect/view/ToolPane.java` constructs the same `DownloaderPane` as `module/tools/ToolsModule.java`; the saved-connection pane strips the tool header. `DownloaderPane.java` shares rows, waiting queue and concurrency across open views in the same application. `DownloadTaskStore.java` uses the original `~/.tomato/downloads.json`.

The Rust tool factory now constructs downloader state for every downloader entry. Both application entry paths prepare it against their active repository's sibling `downloads.json`, so isolated or custom profiles do not fall back to the user's main history. Saved connections retain their ID, name and grouping; their redundant header is hidden. The catalog retains its header. Static history loading does not rewrite either connections or history files.

Each workspace keeps a weak reference to one download actor. Downloader views hold the strong owners and share history, jobs, limits and settings; settings snapshots update every view without replacing an open settings draft. Closing one view keeps the actor available to the other; closing the last view drops the command channel and releases the actor. The weak reference retains no network runtime or file lease. Other tool types do not allocate downloader state or start download workers.

A close/reopen test also reproduced the previous actor's file lease overlapping a new actor's initialization (`target/downloader-shared-1142.log`, `target/downloader-shared-backtrace-1143.log`). Initialization now waits for a lease for at most two seconds, using asynchronous sleeps on the worker. A live owner in another process still prevents access; it is never overwritten. Pending initialization displays a loading label and disables add/settings controls until the original defaults are loaded.

The original history format, unknown fields, first-save backup, external-change guard and bounded HTTP actor remain in use. Saving compares a 20-byte fingerprint of the decoded model: merely opening and closing a sparse legacy file preserves its original bytes and creates no backup. Real changes still verify the original file and back it up before writing. No additional full-history copy or hashing dependency is retained. HTTP/HTTPS range downloads are exercised here; BT/eD2k and other previously listed migration gaps are not marked complete by this repair.

Validation covers factory initialization, both entry paths' real controls (settings, URL rejection, HTTP transfer, byte comparison, record removal), shared history/settings/ownership, repeated immediate close/reopen, lease release and rejection of a different live owner. Network fixtures bind only to loopback; no saved download URLs are contacted. `scripts/qa/downloader.ps1` drives this application's own egui input, captures actual native GPU windows and child dialogs, and performs a real range download through the Add dialog with an exact output hash and legacy-field checks. It does not use operating-system input injection. Final build, native acceptance and memory results follow.
