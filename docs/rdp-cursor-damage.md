# RDP 缺块、双光标与输入调度

本轮针对窗口内黑块/缺块、两个光标拖尾及移动响应迟缓，保持旧连接文件和分辨率设置。

## 拖动反馈复查（进行中）

用户进一步明确：远端桌面中拖程序窗口时，原窗口不动，只有方框随鼠标移动，松开才换位置。直接原因是 IronRDP `PerformanceFlags::default()` 包含 `DISABLE_FULLWINDOWDRAG`，而 Java `Options` 明确排除它。ConfigBuilder 新增可选性能标志覆盖，未设置时仍保留上游默认；Tomato 建连时只去掉此位，保留字体平滑与其他当前偏好。无需修改旧连接文件或要求用户调整远端注册表，重新连接后协商生效。该问题不能描述成网络帧率或鼠标时延已彻底解决；新成品需在真实 110 中确认拖动时窗口内容持续移动。

继续检查到浮动滚动条与远端图片处于同层、区域重叠，不能仅按图片矩形接受鼠标按下。原生输入现在对每次原始按下坐标复用 egui 的精确命中测试；本地滚动条保留本地事件，远端已按下的按钮继续捕获边界外移动和释放。不能仅依赖帧级 `drag_stopped/clicked`：egui 明确不将同一帧内按下并释放算作拖动，实际控件回归已暴露这一情况，故使用逐事件坐标命中。新增真实 ScrollArea 的滚动条拖动和同帧快速拖动回归，旧失败日志保留在 target 下。

814 优化版实连 110 后，用户先确认标签和独立窗口为单光标，随后补充“现在拖动界面移动还是有问题”。后续反馈优先，整体物理验收仍未通过；独立窗口人工测试在等待进一步描述时达到测试时限，退出记录保留为失败，不将超时清理计为正常退出。

对照 Java `FxRdpInput` 的逐事件坐标和按下/移动/释放顺序，发现 Rust 视图原先在处理原始事件前发送一帧的最终 hover 位置。快速拖动可能变成“移动到终点、在起点按下”，而且拖出内容边缘就不再发送移动。现在按原始事件顺序转换坐标，只合并相邻移动，不越过按钮边界；按下成功后捕获边界外移动和释放，坐标限制在远端画布内，非远程区域开始的点击不发送到远端。该修复及原配置 110 的重新验收尚在进行，不能据此认定本地窗口或远端拖动流畅度已解决。

## 本轮输入与退出修复（待最终成品验收）

运行源码冻结清单为 `target/checkpoints/rdp-interactive-810`。鼠标、按键和按钮使用有界的 64 条快速输入队列，由同一 TLS writer 串行写入，与同步图像解码分离。该 writer 使用现有 Tokio 线程，不为每个连接新增操作系统线程；协议响应通过同一 writer 发送，避免字节交错。

剪贴板公告与快速输入共享控制序号：Ctrl+V 等后续输入必须等前序控制响应实际写完。writer 等待这一条件时仍处理协议写入；反激活期间暂停快速输入，重连丢弃旧激活的待发按键。发送失败不发布不可完成的控制序号。

原生 Close 命令安装后主动请求目标窗口重绘，确保事件循环能消费关闭事件；保留取消关闭和未保存内容确认。测试分别记录截图完成、Close 发出和正常退出，超时清理进程不算正常退出。

真实 110 暴露了第二阶段的退出问题：事件循环已经结束，销毁隐藏剪贴板窗口时仍会通过 WM_RENDERALLFORMATS 为每个远端延迟格式等待最多 10 秒。现在由 GUI 所属线程在销毁前设置关闭标记，关闭期间不再发起远端取数；存活时仍按需渲染，不清空其他应用剪贴板，已物化内容保留。可选诊断分别记录标签释放和运行时释放。

私有 Windows 窗口站的回归实际发布多种延迟格式，验证存活时取数、停止应答后 500 ms 内销毁、窗口句柄释放及已物化文本保留。修复版通过；同一个测试加到与冻结 794 哈希一致的旧实现上，在 5 秒后失败，证明覆盖到旧阻塞（`target/rdp-clipboard-shutdown-unit-810/validation.json`、`target/rdp-clipboard-baseline-809/validation.json`）。子进程只使用私有剪贴板。调试器未成功附加，不把这次证据写成调用栈确认。

持续 1080p Progressive 压力测试与成品同样使用两个 Tokio 工作线程，分别记录同步入队、TLS 写完、服务器 handler 和测试观察时间。100 ms 限制施于入队 P95 和 TLS 最大写出耗时，同时要求 32 次输入逐一到达服务器。fixture 的 ironrdp-server 0.13 在持有公共锁时批量写图形，输入 handler 也等待此锁，故其数百毫秒的处理延迟不能直接归因客户端。原先混合指标失败的日志全部保留（798、801、803），没有将它们改称端到端验收通过；真实主机的物理操作另行验收。

实际 110 验证使用原配置的指定连接，只在内存中覆盖标签/独立窗口模式，不保存配置。自动连接、画布与正常退出验证，以及用户移动鼠标/拖动窗口的反馈分别记录。输入写出时间仅表示本地队列到 TLS 写完，不能替代远端响应或物理显示延迟。以下 776 的记录是之前候选版的历史证据，不代表新版本已验收。

## 画布、光标与接收时间改动

- 局部像素块不再被当成整张纹理的尺寸。回退渲染先分配完整画布再上传局部区域，后续远处的更新不会写到小纹理范围外。GPU/回退纹理需要重建时，从服务层保留的完整画布恢复，不依赖服务器再次发送整屏；完整快照共享 Arc，不维护第二份常驻 CPU 画布，也不消费后续脏区域。
- RDP 正常光标接入现有 egui/winit 原生光标桥，移除随 GPU 画面绘制的光标。原生缓存保留图像分配本身，并校验尺寸和热点，避免地址复用选中旧光标。进入/离开远程区域、切换标签以及透明/隐藏光标都会更新可见性。
- 对照 Java FxRdpDisplay 补齐虚拟机画面内光标检测：仅对不大于 24×24 的候选启用，比较移动前后局部像素，连续三次相关变化后抑制重复光标；整屏变化不作为证据。40 ms 探测间隔、400 ms 失配超时、最多 8 组探针、按钮重置及隐藏后位置回报的规则保持原有语义。该检测有界且按需分配，不复制整屏。
- 已排队输入优先于新一轮图像解码；维护、剪贴板等就绪控制消息也先于持续可读的图像流。一个 PDU 内的同步解码仍不能被抢占，不能据此声称所有负载下的真实主机输入延迟都已消除。
- 异步传输记录实际读入的单调时间并传给带宽检测，不再因传入 None 报告零带宽。已缓存的 PDU 保留接收时间，不把解码耗时算成网络接收间隔。时间元数据最多 64 段。
