# RDP 执行与图像上传（2026-10-20）

## 独立协议线程（rdp-worker-348）

排查发现此前虽已减少像素复制、复用纹理并缩短图形合并窗口，RDP 的连接、读包、解码和输入发送仍由 GUI 的 `DesktopSession::poll` 推进。GUI 繁忙、绘制等待或窗口不再轮询时，协议也暂停；大图解码又反过来占用界面线程。以下 334 的单循环公平性修正只能减轻这一耦合，不能解除它。

现在每个 RDP 会话使用一个可取消的 `tomato-rdp` 线程，独立驱动现有异步客户端。输入先于下一批解码转发，网络和协议不再等 GUI 帧。GUI 只读取有界画布上的累计变化、提交纹理并观察任务完成。保留既有 RGBA 多区域、4 ms 合并/解码预算、单事件输出队列和 16,777,216 像素上限；不建立视频帧历史队列。关闭标签或窗口会发送取消信号，协议 future 和 socket 随任务释放。

Windows 原生剪贴板隐藏窗口仍在 GUI 线程创建、保留和销毁。仅将上游明确标注为 `Send` 的 `backend_factory` 交给协议线程，没有给窗口所有者添加不安全的 `Send` 实现。其他平台沿用原有剪贴板后端；连接配置、原生协议、窗口模式和图标不变。

新增真实 TLS/CredSSP + RemoteFX 回归完全不调用 `session.poll`，要求完成握手、解码、发送鼠标输入和关闭后断开服务端。该测试针对本次根因；它不能替代真实主机的端到端延迟测量。

优化成品为 `target/qa-release-rdp-worker-348/release/tomato.exe`，校验和、构建和验收路径记录于同目录 `build-info.json`。401 项默认工作区测试通过、60 项条件测试默认忽略；格式、严格 Clippy、开发全目标构建、优化构建和 CLI 自检通过。1443 个运行源码文件哈希一致，旧配置 59 连接 / 5 分组只读检查通过且共享配置哈希未变；用户原程序与历史发布包未覆盖，没有连接保存主机。

成品实际 GPU TAB/WINDOW 远程画面裁片与先前成品逐像素一致，独立窗口整个客户区一致。开启原生剪贴板的两个窗口也完成连接、绘制和退出；服务端没有提供剪贴板内容往返，不能据此宣称剪贴板数据传输已实测。8 项原生 RDP 回归通过：540 条带完整保留，4 次 GUI 快照，协议测试总计约 132 ms，GUI `poll` 最长约 7.8 微秒；完全没有 GUI 轮询时鼠标送达约 0.36 ms。无后续画面的 32 次鼠标移动 p95 仍约 16.05 ms，包含 Windows 定时与测试循环，不代表真实网络延迟明显下降。

## 先前 334 图像路径与验收（历史记录）

本轮仅调整 RDP 图像从解码到纹理的传递，沿用现有原生 IronRDP、旧连接配置、颜色深度、分辨率、输入协议和窗口设置。没有将用户连接作为测试端点。

## 显示路径

- IronRDP 原生 RgbA32 像素以不换通道的 RGBA 字节顺序发布，补齐不透明 alpha；未收到的初始像素仍为黑色。避免先转成 `0x00RRGGBB` 再在 GUI 转回 RGBA。
- 每次图形提交携带多个变化矩形。只在合并后的面积不超过两块面积之和时合并区域，保留时钟、光标、滚动条等远隔区域。最多 32 个区域；区域总像素超过一个画布时合并为包围矩形，限制暂存数据量。
- services 继续保留一个有界画布，等待 GUI 期间累积变化，避免覆盖尚未读取的区域。重设尺寸时丢弃旧尺寸的变化列表并发布完整画布。
- GUI 将 RGBA 的像素分配直接移交 `ColorImage`，不再逐像素换通道；同尺寸与局部更新使用 `set_partial`，复用 GPU 纹理。旧 RGB 帧读取 API 保留兼容，VNC 与 ADB 的输出格式分别保持。
- 网络输出队列仍只有一个事件；画布上限仍为 16,777,216 像素。使用者关闭会话后按原有 RAII 路径释放资源。

## 图形提交与协作让步

协议图形合并窗口从 16 ms 缩短为 4 ms；GUI 继续按自身显示节拍合并并绘制。只在存在待提交图像时轮询合并计时器，空闲会话不会持续绘制。

解码预算只计同步协议处理和像素准备耗时，累计到 4 ms 后协作让步。网络读取 future 实际返回 Pending 时清零预算，避免把等待网络的时间以及不同空闲周期的解码开销合计后，额外推迟到另一次 GUI 刷新。计数为会话内 AtomicU64，不搬移 Windows 剪贴板所有者，也不增加解码线程。

## 同轮转发与界面公平性

此前解码器与输出接收者由同一个 GUI 轮询推进，随机 select 顺序可能先把空接收者轮询为 Pending，随后解码器才生成消息；已有图像因此要等到下一次轮询。驱动现在固定先推进生产者，再立即接收刚生成的输出。先发布画面，再在每个图像批次后主动让出，避免一个持续有数据的连接占住界面线程。

原生客户端工厂与通用驱动拆开；回归使用有界队列和连续 64 幅立即就绪的图像。测试关闭 Tokio 测试任务的隐式预算，模拟 GUI 手动驱动环境，要求每次轮询立即可见且恰好处理一幅批次，同时保持输入队列的顺序与背压。
